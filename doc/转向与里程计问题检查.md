# RViz 转向但 Gazebo 车体不转：检查记录

**后续实测更新：**用户已经完成下述首轮测试，又运行了完整巡检。短转向通过，但巡检明确出现停车时轮式里程计持续偏转；修订与原始证据见[停车漂移实测与修订](停车漂移实测与修订.md)。下文保留首轮排查经过，不作为最终根因结论。

用户观察为“车体基本不动，可能只有轮子在转”。该现象与轮式里程计把空转累计为车体转角相符，也可能涉及接触受阻、TF 或定位修正。**现有运行日志没有同期真值和编码器轨迹，尚不能把根因确定为某个摩擦参数或 AMCL。**

导航器的 `Goal reached` 是定位估计下的到点判断，不是 Gazebo 真实到点证明。RViz 的 RobotModel 使用 `map → odom → base_footprint`，其中 `odom → base_footprint` 来自四个轮毂的实际关节速度积分；如果轮子空转，它仍可能显示机器人旋转。

## 独立接触测试

检查了四轮转向符号及 URDF 转换后的关节轴。又将实际展开 URDF 中的质量、惯量、关节、球形滚子碰撞体导入系统 libODE，在平面地面上执行左右转向。测试只通过轮毂力矩驱动，不设置车体速度或位姿。

| 指令 | 测量时长 | 真实转角 | 编码器转角 | 平移漂移 |
|---|---:|---:|---:|---:|
| 左转 0.5 rad/s | 3.98 s | 1.102 rad | 1.123 rad | 5.76 mm |
| 右转 -0.5 rad/s | 3.98 s | -1.101 rad | -1.122 rad | 5.70 mm |

独立测试没有复现车体完全不转；它显示当前电机比例控制在这个近似测试中响应偏慢。此测试没有 Gazebo 插件、ROS、相机、真实场地障碍和 Gazebo 自身的 URDF 固定关节合并，**不能据此宣称用户的 Gazebo 已正常**，也没有据此直接调整摩擦或电机增益。

接触参数参考 [Gazebo ODE 物理参数说明](https://classic.gazebosim.org/tutorials?tut=physics_params) 和 [ODE 接触/关节接口](https://www.ode.org/ode-latest-userguide.html)。源代码位于 `smart_community_sim/tests/physics/`。复现：

```bash
source /opt/ros/noetic/setup.bash
cd ~/suanfa_ws/src
xacro smart_community_sim/urdf/community_mecanum.xacro > /tmp/rotation_robot.urdf
python3 smart_community_sim/tests/physics/export_ode_model.py \
  /tmp/rotation_robot.urdf /tmp/rotation_model.txt
g++ -std=c++14 -O2 smart_community_sim/tests/physics/ode_drive_probe.cpp \
  -lode -o /tmp/rotation_probe
/tmp/rotation_probe /tmp/rotation_model.txt 0 0 0.5 /tmp/rotation_left.csv
/tmp/rotation_probe /tmp/rotation_model.txt 0 0 -0.5 /tmp/rotation_right.csv
```

## 已补充的实际诊断

1. `drive_test.launch verify:=true rotation_only:=true`：在空地通过真实键盘节点发送左转、右转和停车，读取 Gazebo 位姿、四轮接地信息及同时间戳的 `/simulation/ground_truth` / `/odom`。终端打印真实转角、编码器转角和误差；JSON 记录运动是否成立、里程计是否一致，CSV 保留连续轨迹。转向测试之外保留松键停车检查。
2. 通过条件增加相对位移误差 ≤ 5 cm、转角误差 ≤ 0.15 rad，且每个动作阶段四个轮组均有接地记录。该条件不表示四轮在每一瞬间都同时接地，接地记录也不能替代摩擦力测量。
3. 驱动插件每 2 秒写 `drive_check`：指令速度、编码器速度、真实车体速度、两套位姿及四轮速度。最新修订中角速度差超过 0.03 rad/s 或平移速度差超过 0.02 m/s 持续 1 秒，会记录 `DRIVE_ODOMETRY_MISMATCH`。这仅用于报告，不用仿真真值修改 `/odom`、TF 或电机输出。
4. 普通 `patrol.launch` 默认开启被动诊断记录，退出后输出 `/tmp/community_patrol_diagnostics/本次时间戳/trajectory.csv` 和 `report.json`。它不发控制指令，退出也不终止巡检。正式对比入口复用原有测评节点，不重复启动记录器。

## 下一次验证

关闭当前巡检、Gazebo 和键盘控制。先重新编译，确保加载带诊断的新插件：

```bash
cd ~/suanfa_ws

source devel/setup.bash
roslaunch smart_community_sim drive_test.launch verify:=true rotation_only:=true \
  2>&1 | tee /tmp/community_rotation.log
```

测试结束后检查 `/tmp/community_motion_report.json`、同名 `.csv` 和 `/tmp/community_rotation.log`。这一轮不启动 AMCL 或 DWA，能区分底盘自身问题与导航/定位问题：

- 空地也出现“编码器转、车体不转”：先检查轮地接触、空转和 Gazebo 物理/插件行为。
- 空地转向和里程计均通过，完整场地才不转：查看接触受阻及普通巡检新记录的指令、真实轨迹、定位轨迹。
- 真值与 `/odom` 一致，但 RViz 定位姿态偏离：再检查 AMCL、激光匹配和 `map → odom` 修正。

当前执行环境仍禁止本地 socket 绑定，不能代替用户启动 ROS/Gazebo 完成这轮在线测试；上述诊断已实现，但现场根因和修复效果仍待这些数据确认。
